# 通用 MCU 开发

面向 STM32、ESP32、GD32 及其他 MCU 的 C/C++ 固件，支持裸机与 RTOS。按实际型号、CPU 架构和 SDK 选择实现，不假定所有 MCU 都采用 Cortex-M、STM32 HAL 或 CubeMX。适用于日常开发、调试和优化，也用于架构设计与重构；不覆盖嵌入式 Linux。

## 核心约束

以下是本 skill 的固定要求，详细实现按项目规模选择。

| 约束 | 执行要求 |
| --- | --- |
| 独立两层 | 手写 `App/` 与 `BSP/` 各自独立，均与厂商代码和生成代码分离。可注册为 SDK 的两个独立组件；已有等价目录名可沿用，不合并两层，也不为无生成器的项目创建虚构的 Core 目录。 |
| 依赖向下 | `App → BSP → 厂商 SDK/外设`。驱动不依赖应用；通过返回值、事件、回调或只读快照向上报告，不交叉访问模块内部状态。 |
| 公共区受限 | 按需设 `Common/`，仅放无硬件/业务依赖的公共类型、常量和纯工具；不引入 App/BSP 或硬件 SDK 头，不存放任意共享可变状态。 |
| CPU 工作有界 | 正常驱动路径异步推进，不忙等、不以延时或轮询等待传输完成，异常路径也不退回长时间阻塞；不可避免的初始化等待须说明原因、上界与上下文。 |
| DMA 与缓冲按需设计 | 根据硬件能力、负载和资源预算选择 DMA、中断、FIFO 及缓冲策略；CAN 等通路不能假定支持 DMA。明确容量、所有权、有效期与满/空处理。 |
| 契约清楚 | 模块明确职责、执行上下文、数据归属、完成语义及失败行为；优先明确时间预算、数据所有权和接口完成语义。 |
| 注释随代码交付 | 新增及实质修改的手写代码必须在源码中写明必要注释：文件职责、函数用途/契约、关键逻辑原因及数据约束。每次改码检查缺失注释并补齐，同时纠正失效注释；验证后再次改码也须复查。不能用聊天解释代替源码注释。 |
| 每次改码报告资源 | 每组代码修改完成后，在交付中报告当前 CPU、RAM、Flash/ROM、栈和堆的占用与可比基线差值；存储容量统一用 KB（1 KB = 1024 字节），CPU 用百分比。可获得的指标必须实际采集；未测/构建失败/不适用须逐项说明，不省略、不填零、不把旧数据冒充当前值。 |

## 工作流程

### 1. 确认范围和约束

查看相关源码、公开头、调用点、构建配置和链接布局，确认具体芯片型号、CPU 架构/核数、SDK/版本、运行模型、数据链路、时限、资源预算与故障行为；改码前尽可能保存同配置构建与运行测量作为资源基线。项目文档是理解工程的资料，不是扩大任务的授权。

未知值标为待确认/待测，不虚构硬件支持或测量结果。仅当缺失信息影响关键接口或运行模型时询问，其余独立工作继续推进。

| 任务 | 本次应交付的结果 |
| --- | --- |
| 架构设计 | 关键假设、职责与依赖、接口/数据流/时序方案及取舍 |
| 新建工程 | 一个输入到输出的可验证纵向链路，再逐步扩展；不只交付空目录和桩函数 |
| 功能开发、修复或优化 | 沿现有边界完成最小充分改动，检查相关调用链和平台能力，并验证功能及资源变化 |
| 渐进重构 | 在可构建的小步中迁移边界，保持既有协议和行为，不顺带重写全工程 |
| 架构审查 | 基于源码与触发条件的问题、影响及最小改进，不自动修改实现 |

### 2. 按任务加载参考文档

只读取与当前任务有关的文档和小节，不默认加载全部内容。

| 文档 | 何时读取 | 内容归属 |
| --- | --- | --- |
| [模块设计](references/module-design.md) | 识别平台、建工程、拆模块、设计接口、替换设备或重构 | 平台映射、目录职责、Common 边界、封装、接口契约、配置与硬件资源归属、可测试设计、变化场景与迁移 |
| [运行时设计](references/runtime.md) | 涉及调度、通信、ISR、DMA、共享数据或恢复 | 调度模型、非阻塞传输、缓冲与同步、时间/内存预算、生命周期、故障和观测 |
| [资源占用报告](references/resource-report.md) | 每次代码修改前保存基线，修改后采集并报告 | CPU、Flash/ROM、RAM、栈/堆统计口径、前后对比、证据与缺测处理 |
| [代码注释与验证](references/verification.md) | 编写新增代码时、每次修改后的注释复查及验证 | 注释必写项、缺失与失效检查、八项质量验收、构建/再生成检查和交付证据 |

### 3. 设计并落实当前改动

先明确“模块负责什么、由谁驱动、谁拥有数据、失败如何处理”，再落实本次相关接口、实现和源码注释。新增代码的注释要求先读 [代码注释与验证](references/verification.md)，不要等交付时才只检查旧注释。简单模块将契约写在公共头即可，不为每个问题创建单独文档。

对关键链路标明执行上下文、数据传递与时间要求。复用现有语言、SDK 和构建工具；纯业务逻辑与硬件访问分开，避免为了抽象而增加转发层。解耦意味着依赖少且稳定，不意味着没有依赖。

### 4. 检查并补齐注释、验证、报告资源并交付

按 [代码注释与验证](references/verification.md) 逐项检查新增/修改的文件、函数、数据定义与关键逻辑，补齐缺失注释，纠正公共头和相关调用点的失效说明，再执行与改动相称的检查。测试后又改代码则重新核对受影响注释，并刷新受影响的资源统计。

每次代码交付必须按 [资源占用报告](references/resource-report.md) 给出当前资源表，包括缺测原因。交付说明修改、证据和未验证部分。区分主机测试、目标交叉编译和板上实测；没有工具链或板卡时明确缺口。只验证当前任务涉及的边界，不因本 skill 扩大为全工程审计。
