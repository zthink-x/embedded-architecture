# 运行时设计

用于调度、非阻塞驱动、数据并发、资源预算和故障恢复。接口契约见 [模块设计](module-design.md)，验证和交付见 [代码注释与验证](verification.md)。

## 执行模型与调度

已有可满足要求的模型优先保留。裸机适合可拆为短步骤的有限任务；当多条链路必须独立等待、优先级调度或需要相关内核服务时再评估 RTOS。RTOS 不会自动保证实时性或解决数据竞争。

裸机：

- 将周期任务和事件消费集中在可理解的调度点，每轮工作有界。
- 明确周期是“相对上次完成”还是“按绝对时间释放”，以及任务超期时丢弃、合并、补执行还是降级。
- tick 标志仅表示至少有一次请求；不能用它承诺处理每次事件。需要保留次数时用合适的计数或队列，并处理溢出。
- 检查一次最慢任务对其他任务响应时间的影响，不只计算平均 CPU 占用。

RTOS：

- 按时限、阻塞行为和资源所有权分任务。给出周期/事件源、优先级理由、栈预算和通信方式；不要每个模块都创建独立线程。
- ISR 仅使用该内核和端口允许的接口，核对中断优先级限制；实际 API 以当前工程内核版本为准。
- 队列用于传递数据/工作项，通知或信号用于唤醒，互斥用于串行保护资源；选择依据语义而不是统一套用一种原语。
- 共享资源识别锁顺序、等待上界和优先级反转；不要持锁执行不受控的 I/O，也不要跨模块形成循环等待。

多核或带后台系统任务的平台另行核对：

- 多核共享数据采用 SDK/内核支持的跨核同步；只关闭当前核心中断不能保护另一核心的访问。任务绑核只有在时延或外设约束确有需要时才设置，不默认固定全部任务。
- SDK 回调可能来自 ISR、事件循环或工作任务，按实际上下文选择调用和等待方式；不能把所有外设回调都视为中断。
- 涉及 Flash 操作、缓存暂不可用、外部 RAM 或省电状态时，核对回调代码、访问数据和 DMA 缓冲的实际限制；不在所有芯片上机械套用 IRAM、DTCM 或固定内存属性。
- 无线协议栈等后台任务与 App 共用资源；CPU 和内存评估覆盖实际启用的服务和负载，不能以禁用后台服务的空载结果代表部署状态。

ESP-IDF 的具体调度和临界区行为参见 [对应目标的 FreeRTOS 文档](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/freertos_idf.html)；单核/多核与相关配置以工程版本为准。

ISR 只承担符合时延预算的确认中断、采样/搬运、发布事件或必要的有界快速控制；复杂业务交给主循环/任务。不是所有 ISR 都只能置标志。

## 非阻塞驱动与外设传输

- 驱动以“提交 → 进行中 → 完成/失败”推进事务，接口区分请求接受和真实完成；拒绝忙等 TX/RX 标志、DMA 完成或队列腾空。
- DMA 适用于目标硬件支持的通路。先核对芯片、SDK 和通道资源；SPI/I2C/UART 根据长度、频率和启动开销选择 DMA 或中断，CAN 不能假定具备同样能力。
- CAN 发送遇硬件 FIFO/邮箱满时，返回忙碌或进入有界软件队列，完成通知再推进；接收按吞吐与 ISR 预算搬运/发布数据，不在 ISR 中执行应用控制逻辑。
- 仅在设备协议允许的事务边界拆分长传输并安排关键工作，不能为调度破坏 SPI 片选连续性、命令/数据顺序或 I2C 重复起始序列。不能拆分的事务计入最长总线占用预算；总线占用与 CPU 占用分别分析。
- 区分 DMA 数据搬运结束、外设在线路上发送结束和对端确认；确认实际硬件与 SDK 回调语义后，才释放片选、切换总线参数或关闭外设。不可凭 DMA 完成标志提前结束总线事务，也不能用无界忙等补偿这一差异。
- 减少不必要的半传输/逐字节中断、重复内存拷贝和无变化刷新，但保留正常完成、错误检测和恢复所需事件；不可为降低中断数关闭必要通知。
- RTOS 任务等待事件时可以让出 CPU，但这不等于接口立即返回；文档分别说明调用方是否等待、CPU 是否被占用和超时范围。实时 App 路径仍优先异步接口。
- 无法使用 DMA 时选择硬件 FIFO、中断、批量或短步骤状态机。优化目标是有界的 CPU 工作量，不把全部工作简单移到高频 ISR。
- LCD 可采用脏区域/行合并和分块发送，减少无变化刷新；优化前后比较相同负载下的 CPU 时间、事件负载、端到端延迟及 RAM 使用。
- 不可避免的硬件初始化等待优先分阶段推进；确需等待时记录原因、上界与调用上下文，不能称作非阻塞接口。

## 数据所有权、同步与缓冲

| 数据需求 | 可选机制 | 必须说明 |
| --- | --- | --- |
| 只关心最近测量 | 最新值槽、覆盖队列或快照 | 时间戳/有效性，多字段是否同一采样批次 |
| 每条命令必须处理 | 有界队列 | 容量、满时反馈、是否确认完成 |
| 连续接收字节 | 环形缓冲或 DMA 分块 | 读写边界、覆盖检测、重同步 |
| 事件只需唤醒 | 标志/通知 | 合并事件是否允许 |
| 必须保留事件次数 | 有界计数或队列 | 溢出与消费速率 |

- 为共享状态明确一个拥有者；其他模块通过请求、只读接口或消息交互。
- 检查“读取/处理/清除标志”和“检查队列/进入等待”的并发窗口，避免清掉新事件或丢失唤醒；使用符合目标平台的原子交接、短临界区或 RTOS 同步接口，不能把分开的读取与清零当作原子操作。
- `volatile` 不能代替互斥、原子操作或多字段一致性协议。选择同步方法时核对目标架构、编译器及内核保证。
- 临界区保持短小；避免在 ISR 中忙等被中断任务持有的资源。双缓冲同样要定义发布时机、内存可见性与读者释放规则。
- 借用缓冲必须有完成/取消后归还的规则；队列只复制指针时不等于复制了负载。
- 容量依据峰值到达率、最大消费者停顿和允许突发估算，之后实测。平均吞吐足够不代表不会溢出。
- LCD 根据 RAM 预算选择整帧、局部行/块或双缓冲；DMA 正在读取的区域不被无约定地覆写，允许撕裂的策略也须明确。
- 命令队列和最新设定值不能混淆：只有允许覆盖的目标更新才能合并，启停、校准等离散命令不能擅自丢弃。反馈快照带有效性/时间信息，避免消费陈旧数据。

## 关键路径的时间预算

为本次涉及的关键链路记录下表，简单系统可直接写在接口或调度说明中。未知值标为待测，不填写看似精确的猜测值。

| 项目 | 记录内容 |
| --- | --- |
| 触发与目标 | 周期/事件源、截止时间、允许抖动、数据最大年龄 |
| CPU 工作 | ISR、计算、拷贝、驱动启动和其他高优先级任务干扰 |
| 等待与传输 | 队列等待、共享总线仲裁、硬件传输、必要的对端响应 |
| 资源竞争 | 最大不可抢占区间、锁等待、队列中低优先级工作的影响 |
| 余量与失败策略 | 预算余量，超期的跳过/合并/降级行为及恢复条件 |
| 验证条件 | 测量位置、时钟/负载配置、最大观察值、尚未覆盖的条件 |

- 区分每个阶段的 CPU 耗时与端到端经过时间；并行阶段不能简单全部相加，沿实际关键路径分析。
- DMA 释放 CPU 不会消除总线排队。大块低优先级刷新仍可能延迟关键事务，按需分块或安排优先级，并避免其他工作长期饥饿。
- 不把平均 CPU 占用低作为满足截止时间的证据；测量高负载、突发输入和恢复路径。实测最大值不等于理论最坏执行时间证明。
- 优化前后比较同等负载下的时延与资源指标，不用一次正常运行证明全部条件满足。
- 时间间隔比较考虑计数器回绕，说明适用的计数宽度和最大间隔。

## 内存预算与 DMA 存储

- 内存预算包含静态数据、堆、各任务/中断栈、队列、帧缓冲及 DMA 存储。是否允许动态分配由可预测性和生命周期决定，不一概禁止。
- DMA 缓冲必须满足目标芯片的可达内存、对齐和生命周期要求；缓存/MPU/一致性按实际硬件配置处理，不复制其他芯片的段名或缓存操作。
- 明确 DMA 与 CPU 在何时取得/交回缓冲所有权；启动失败、半传输、完成、超时和取消路径均不得泄漏或提前复用缓冲。

## 生命周期与故障恢复

模块按需要区分未初始化、初始化中、就绪、运行、停止中和故障状态；简单模块可合并不必要的状态，但必须定义其行为，不能只提供一个 Init 函数而忽略退出路径。

- 按依赖顺序初始化时钟/内存、外设、设备和 App 状态。只有满足先决条件才发布就绪状态，提前启动的 ISR/任务不能访问未初始化数据。
- 规定未就绪时调用、重复初始化、重复停止和故障中调用的结果；初始化部分失败时释放已经取得的资源，不返回虚假的成功。
- 停止时决定是否拒绝新请求、排空还是取消队列，结束硬件访问后再回收资源；处理迟到的回调，避免污染新一轮运行状态。
- 恢复时重新确认设备和数据有效性，清理或标记旧事件、旧反馈和过期命令。电机断线恢复后不能未经判断就执行断线前积压的动作。

在设计正常路径时同时列出相关故障路径：

| 故障 | BSP 提供的事实 | App 决定的行为 |
| --- | --- | --- |
| 传感器断开/反馈过期 | 错误原因、有效性、最后更新时间 | 停止使用陈旧值，按产品需求降级或停止 |
| 总线拥堵/队列满 | 忙碌、占用、拒绝或丢弃计数 | 合并允许覆盖的目标、降低非关键负载或报告失败 |
| DMA 启动/传输失败 | 请求结果、资源状态、错误计数 | 有界重试或退出；不回退到长时间阻塞 |
| 初始化失败/设备重启 | 可用性、完成阶段、恢复结果 | 决定是否允许部分运行及何时重新使能 |

- BSP 报告可判断的事实，App 管理产品级策略；重试有次数/总时间上界，必要时设置间隔，不能形成持续高负载重试循环。
- 故障后的输出和恢复条件由产品定义，不统一假定置零、复位或立即重启就是正确行为。
- 重试前区分“确定未执行”和“结果未知”；设置目标值等可重复操作与起跳/校准等一次性动作分别处理。非幂等命令在超时后不能盲目重发，按协议能力选择序号去重、状态查询或上报不确定结果。
- 如使用看门狗，以关键任务实际推进及数据处理结果判定健康，不能由仍在运行的无条件定时器掩盖业务卡死。
- 按需注入断连、超时、满队列和完成/取消交错，验证系统仍能调度、资源可回收且不会发出过期指令。

## 运行可观测性

每次改码交付时，CPU、RAM、Flash/ROM 和栈/堆的统计方法与报告格式遵循 [资源占用报告](resource-report.md)。下列诊断指标按任务相关性补充。

按当前链路需要保留少量低成本指标，而不是建立全工程高频日志系统：

| 类别 | 典型指标 |
| --- | --- |
| 实时性 | 任务耗时最大观察值、释放到完成时延、超期/丢拍次数 |
| 通信 | 发送忙、超时、校验错误、丢帧及恢复次数 |
| 缓冲与内存 | 队列高水位、溢出次数、栈余量（工具支持时）、分配失败 |
| 数据与健康 | 最后有效反馈时间、数据年龄、故障状态、复位原因（平台支持时） |

- 每个指标说明单位、更新时间、采集点、复位方式以及计数饱和/回绕策略；跨上下文读取遵守一致性要求。
- ISR/实时路径优先更新计数或记录短事件，在低优先级上下文限频输出；字符串格式化与大量串口打印不能侵占控制预算。
- 诊断队列容量有限，满时允许按策略丢弃诊断并计数，不能反向堵塞业务。
- 默认只采集有明确用途的指标，较重的跟踪可以按配置启用；比较开启/关闭观测时的开销，避免测量本身改变被测行为。
- 定位问题时关联错误计数、数据年龄和时延，不仅报告“运行正常”；明确采样时长、负载和覆盖范围。

## 相关机制的官方依据

以下资料用于理解具体机制，不替代目标芯片参考手册、勘误和工程实际 SDK 版本：

- [ST AN5543：SPI 通信](https://www.st.com/resource/en/application_note/an5543-enhanced-methods-to-handle-spi-communication-on-stm32-devices-stmicroelectronics.pdf)，尤其是数据流及 DMA/总线完成时序；芯片版本之间的完成标志并不统一。
- [FreeRTOS：任务通知](https://github.com/FreeRTOS/FreeRTOS-Kernel-Book/blob/main/ch10.md)，用于核对等待、读取与清除通知的语义；不要求裸机工程引入 RTOS。
