# 模块设计

用于工程组织、模块拆分、接口设计与渐进迁移。运行时细节见 [运行时设计](runtime.md)，改码后检查见 [代码注释与验证](verification.md)。

## 工程目录与启动边界

本规范中 `BSP/` 统一承载手写设备驱动、共享总线管理与板级适配；厂商 SDK 目录保持原名，既有 HAL/CMSIS 的 `Drivers/` 不改名。

App 与 BSP 必须是独立的手写目录/组件，与 SDK 和生成代码分离；有 CubeMX 时独立于 Core。按项目规模增加层内子模块，不机械增加顶层层次。以下是 CubeMX 工程示例，其他 SDK 按下节映射，不要求全部创建：

```text
Core/                    CubeMX 生成的初始化、入口与中断桥接
Drivers/                 厂商 HAL/CMSIS（如存在）
BSP/                     手写驱动层
  lcd/                   SPI 屏幕协议、显示原语、异步刷新
  motor/                 CAN 电机命令编码、发送与反馈解析
  sensor/                I2C/SPI 传感器
  bus/                   共享总线管理（按需）
  port/                  板级绑定与适配（按需）
App/                     手写应用层
  scheduler/             应用初始化、周期/事件调度
  menu/                  UI 页面与交互
  control/               控制算法、产品状态机
Common/                  无硬件/业务依赖的公共基础定义（按需）
```

- 保留平台要求的启动入口：CubeMX 工程由 Core 的 `main` 调用 App，ESP-IDF 工程可由 `app_main` 组织应用启动，其他 SDK 沿用其启动模型。入口负责装配，不堆放完整业务实现。
- 采用 HAL 全局回调覆盖方式时，每个回调只有一个明确实现者，按实例分发；SDK 支持实例回调注册时可使用注册机制。无论哪种方式都明确回调归属，避免重复定义或覆盖别的模块注册。桥接可放在生成代码的用户区或独立适配文件。
- BSP 可使用目标 SDK 的驱动/固件库和实际存在的外设声明；App 调用设备级接口，不散布具体芯片寄存器或外设操作。同步登记源文件、组件依赖和包含路径。
- 生成区域改动遵循工具扩展边界，保留再生成能力；不修改厂商库来夹带产品行为。

## 平台映射与能力确认

架构约束共用，入口、构建、同步与外设实现按平台选择。不要仅替换芯片名称或 HAL 函数前缀就认为完成移植。

| 平台/工程 | BSP/App 如何落地 | 实现前应核对 |
| --- | --- | --- |
| STM32 + CubeMX | Core/Drivers 保持厂商边界，手写 BSP/App 独立登记 | 具体系列、HAL/LL 或现有库版本、时钟、中断、DMA 与内存布局 |
| ESP32 系列 + ESP-IDF | 可使用 `components/BSP` 与 `components/App`，由 `main` 组件的入口装配；也可用工程已注册的等价独立组件 | `IDF_TARGET`、IDF 版本、CPU/核数、组件依赖、sdkconfig、分区表和实际外设支持 |
| GD32 | 保留所用系列的启动代码与固件库，分别编译手写 BSP/App | 精确型号、内核架构、固件库版本、外设时钟/寄存器/标志及中断语义；不能假定与相近 STM32 型号等价 |
| 其他 MCU 或其他开发框架 | 沿用官方工程入口与构建方式，以独立目录/库表达 BSP/App | 使用的 SDK/框架、运行模型、工具链和可用硬件能力；不默认迁移到 ESP-IDF 或 STM32 工具 |

- `components/BSP` 和 `components/App` 是目录映射示例，实际大小写、组件登记和依赖声明保持工程一致；平台已有同名 BSP 时先核对其职责，避免组件重名和覆盖。
- 构建优先使用工程自身入口和目标工具链，如项目已有的 ESP-IDF、CMake、Make 或 IDE 工程；不混用不同 SDK 的配置或构建产物。
- 外设数量、CAN/TWAI、DMA、缓存、外部 RAM 和计时器能力都以具体芯片与 SDK 为准，不从“ESP32/GD32/STM32”系列名称推断支持情况。
- SDK 已提供总线队列、锁、DMA 或完成通知时优先复用，在 BSP 内补充设备协议与缺失能力，避免重复接管底层硬件。
- 业务层可复用平台提供的网络、存储等高层服务，通过清晰接口隔离；BSP/App 约束不要求把所有系统 API 包装成无意义的 BSP 转发函数。

官方参考：[ESP-IDF 组件构建](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/build-system.html)、[GD32 官方固件库与资料](https://www.gd32mcu.com/en/download)。访问文档时选择工程对应的芯片和 SDK 版本，不能把链接当前默认版本当作项目版本。

## 职责划分与公共区

LCD 驱动提供绘图/刷新能力，App/menu 决定页面内容；电机驱动提供命令和反馈，App/control 决定目标值和动作。使用 CAN 控制带 FOC 的电机，不等于必须在主控驱动中实现 FOC 算法；按实际控制器职责确定。

多个设备共享 SPI/I2C 时，由驱动层总线管理串行化事务并明确片选、模式与缓冲生命周期；设备模块不通过彼此的私有状态协调。功能协同放在 App 中，底层不引用上层头。

公共区只容纳确实被多模块复用且归属中立的纯定义或工具：

- 可以放共享单位、稳定的数据类型、纯数学工具和通用结果类型，按主题拆小头文件。
- 设备寄存器、量程及协议细节留在对应 BSP；产品模式与策略留在 App；板级句柄和引脚留在驱动适配或生成配置中。
- 不放跨模块任意读写的全局运行状态，不建立包含所有模块的 `common.h`，也不以 Common 绕过依赖方向。
- 某模块拥有的数据通过公开接口、只读快照或消息传递。可共享数据不等于共同拥有写权限。

## 封装、状态与参数

- 公共头只暴露使用者需要的能力；私有函数和状态收在实现中，跨实现文件的内部声明收在内部头。避免业务直接改写驱动全局变量。
- 按实际实例数选择单例或上下文对象；多设备/多链路场景使用实例化状态，不强制所有小模块都面向对象化。
- 长流程用显式状态机表示进入条件、事件/时间推进、退出动作和异常路径；避免以长延时或轮询死循环表达业务步骤。
- 参数分别归属板卡配置、设备协议、产品配置与运行状态。共享量程/映射只维护一个可信来源；不要制造全工程巨型配置头。
- 数值接口说明单位、符号、坐标系和有效范围；协议接口说明长度、字节序、版本与校验。精度和数据类型按处理器能力与误差预算选择，不固定为 float。
- 命名沿用现有工程；新工程可用模块前缀函数、私有状态、定宽协议字段及一致头文件保护。代码风格服务于边界清晰，不是本 skill 的主要产出。

## 抽象边界的选择

| 情况 | 适合的选择 |
| --- | --- |
| 一块固定板、一次性小功能 | 在 BSP 内直接使用既有厂商驱动库，App 只调用设备接口，保持私有状态 |
| 同一设备将接入不同总线/平台 | 设备协议与传输拆开，注入有明确语义的 transport |
| 同一算法有不同输入来源 | 算法只接收值/状态，不让算法主动读取设备 |
| 多个功能共享总线 | 明确总线所有者或仲裁者，限制并发入口 |
| 多项业务需要共享策略 | 在 App 内建立共享模块，不新增必需的顶层服务层 |

transport 接口要明确同步或异步。不能让同一个 `write()` 在不同 port 中分别表示“复制完”“排队成功”和“线上发送完成”，却不告诉调用者。

## 公共接口契约

新增或实质修改的公共接口必须将适用契约写进头文件注释；私有函数也要在定义处说明用途和必要约束，具体见 [代码注释与验证](verification.md)。按接口实际行为填写下列项目，简单接口用简短注释即可：

| 项目 | 应说明的内容 |
| --- | --- |
| 职责与调用者 | 服务谁、允许哪些入口、哪些行为交给上层 |
| 生命周期 | 初始化先决条件、重复初始化语义、运行、停止、恢复 |
| 数据 | 参数范围/单位、输入借用还是复制、输出所有权和有效期 |
| 并发 | 可调用的上下文、是否可重入、谁序列化访问 |
| 时间 | 同步/异步、等待上界、截止时间与取消语义 |
| 完成与失败 | 已接受/已完成的区别、回调上下文、错误返回、队列满策略 |

异步发送的契约示例：

- 分开定义“已接受”“本地传输完成”“对端确认/执行完成”；接口只承诺其实际能观测的阶段，没有应答协议时不伪造对端确认。
- 提交被拒绝时不转移缓冲所有权；已接受的请求通过明确的完成/失败/取消机制收尾。多请求并发时使用请求标识或等效关联方式，避免反馈对应错请求。
- 明确选择“调用时复制数据”或“借用缓冲至完成通知”，不能混用。
- 队列满返回忙碌；由调用方按业务决定丢弃、合并或有界重试。
- 完成通知说明成功/失败/取消及执行上下文，并规定是否可能在提交函数返回前触发、能否重新提交请求或调用停止接口。实现须防止锁内回调造成死锁、同步完成造成递归链或初始化顺序错误。
- 停止过程中处理未完成请求，确保硬件不再访问缓冲后才归还所有权。规定取消与完成同时发生时的裁决方式，避免重复通知或重复释放。
- 反馈接口携带必要的有效性、时间信息；陈旧值、尚未获取到数据和真实零值应可区分。

这是接口语义示例，不要求项目统一采用某个函数名或错误枚举。

## 配置与硬件资源归属

- 引脚、时钟和总线实例归板级配置；器件寄存器和协议量程归设备；采样频率、产品模式与告警策略归应用/服务。
- 常量配置和可变运行状态分开。需要持久化配置时才设计版本、默认值、校验与掉电恢复，避免给无存储需求的项目强加配置系统。

- 接入新外设或多实例时，按需列出引脚复用、外设实例、DMA 请求/通道、中断优先级和共享时钟的拥有者；启动前检查冲突，不能让后初始化模块静默覆盖配置。
- 共享总线的配置修改、复位和恢复由总线拥有者协调，通知或结束受影响事务；单设备故障不能擅自复位仍服务其他设备的共享外设。

故障决策、重试边界和诊断开销统一见 [运行时设计](runtime.md)，不在模块中各自发明恢复策略。

## 可独立测试的逻辑

- 控制算法接收测量值、目标值、参数和显式状态，返回结果；不要在算法内部隐式读取硬件 SDK、等待设备或打印日志。
- 协议编解码接收字节与长度，输出结构化结果或错误；将实际收发与纯解析分开，但都可保留在对应 BSP 模块内。
- 输入边界先检查长度、索引、字段范围与长度运算溢出，再访问或复制数据；解析的单次工作量和缓存上限有界，错误输入不能触发越界或无限重同步。
- 不把线上字节直接强转为未验证布局的 C 结构体；显式处理字节序、对齐与字段宽度。控制/配置入口按算法要求校验范围及非有限浮点值，约定拒绝还是限幅。
- 状态机以事件、数据和传入的时间推进；用可替换的时间源验证超时，不依靠测试中的真实长时间等待。
- 通过小型替身模拟传输忙碌、失败和完成事件，测试应用决策；替身必须遵循真实接口契约，不能把所有操作都伪装为立即成功。
- 主机测试覆盖逻辑，目标交叉编译覆盖真实接口与链接，板上测试覆盖电气/时序与硬件资源。测试通过时明确属于哪一类证据。

## 用变化场景检查解耦

| 变化 | 主要允许受影响的位置 | 应检查的耦合信号 |
| --- | --- | --- |
| 换 LCD 型号 | BSP/lcd、硬件绑定；能力变化时调整相关 App | 菜单散落寄存器、SPI 句柄或器件初始化序列 |
| 改电机通信协议 | BSP/motor、相关配置/装配 | 菜单、调度、控制算法各自打包同一种协议 |
| 改菜单或产品模式 | App 中相关功能模块 | 必须修改底层收发才能调整业务流程 |
| 增加同类设备实例 | 驱动实例配置与应用装配 | 私有状态被不必要地写死成不可区分的全局变量 |

变化场景是检查方法，不是强制兼容一切硬件：新设备能力或单位契约确实变化时，上层可以合理调整。优先稳定设备能力接口，将厂商差异集中在驱动内；不要为假想扩展预先制造层层接口。

## 新建与渐进重构

新建项目先实现“一个输入 → 一项处理 → 一个输出”，验证构建、初始化、数据流和失败路径后再扩展。若板卡尚未确定，明确交付是可测试的核心逻辑和待接入适配边界，不宣称完整硬件工程。

重构时：

1. 记录现有入口、协议、时序和外部可观察行为。
2. 找出本次主要耦合点，例如业务直接操作 UART 或多个模块各自解析同一协议。
3. 提取小接口并保留兼容调用，逐个迁移使用者。
4. 同步构建登记、初始化顺序和数据所有权，每个阶段保持可构建。
5. 确认无引用后移除旧实现，避免长期保留两份真相源。
6. 每次改动后补齐新增或实质修改代码的必要注释，并核对受影响的源码/头文件/调用处注释，尤其是迁移后的职责、调用上下文和完成语义。
