# 代码注释与验证

新增及实质修改代码时写好必要注释；修改后检查缺失与失效两类问题，再按改动选择验证。测试中再次改码时重复注释核对。此文档是检查入口，机制设计分别见 [模块设计](module-design.md) 与 [运行时设计](runtime.md)。

## 编写代码时必须添加的注释

注释是代码交付的一部分。适用于本次新增或实质修改的手写代码，包括 `static` 内部函数；不能以“命名已经清楚”或“最后会解释”为由省略函数用途、接口约束和关键实现理由。默认用中文解释，标识符和协议字段保留英文；工程有明确注释语言规范时沿用。

| 代码对象 | 必须写清的内容 | 放置位置 |
| --- | --- | --- |
| 新增 `.c/.h` 文件或职责发生变化的模块 | 模块用途、边界、主要入口；有硬件/上下文约束时一并说明 | 简洁文件头，不捏造作者、日期或历史 |
| 新增/实质修改的函数，包括内部函数 | 用途；参数/结果中不直观的语义、单位和范围；适用的失败行为、上下文、阻塞性或副作用 | 公共 API 的调用契约以头文件为准；私有函数在定义前说明 |
| 数据结构、枚举和重要字段 | 类型用途；字段的单位、范围、状态含义和有效条件；有共享状态时说明读写方 | 类型前与相关字段/枚举值旁 |
| 参数宏、阈值、映射表和固定长度缓冲 | 物理/协议意义、单位、合理的来源或选择依据；缓冲容量与所有权约定 | 定义处或对应表前；未知依据如实说明，不编造 |
| 非直观算法或关键控制块 | 目标、公式/坐标系、边界保护与处理顺序的原因；关键状态转换的触发和退出条件 | 对应逻辑块前，避免只在文件头笼统提及 |
| ISR、DMA、并发和错误恢复路径 | 执行上下文、同步与所有权转移、完成/取消含义、超时或回退选择的理由 | 相关入口、状态或分支附近 |

按函数复杂度控制长度：简单私有函数用一句有信息量的用途说明即可；公共或复杂函数可用 `@brief`、`@param`、`@return`、`@note`，只填写适用项，不堆空标签。公开契约无需在 `.h` 和 `.c` 逐字复制，实现在关键位置补充理由与约束。

注释要帮助后续维护者理解代码：

- 写“为什么这样做、哪些条件必须成立、改变后会影响什么”，不把 `count++` 翻译成“计数加一”。
- 对普通赋值、显然的循环和每个局部变量不机械加注释；对单位、魔数、位运算、临界区和异常选择不能仅凭名称略过。
- 复杂函数按有意义的处理阶段加块注释，不按固定行数插入分隔线；不以注释行占比作为质量指标。
- 将说明写入实际源码，聊天总结和独立文档只作补充。注释必须与实现一致，不能写“非阻塞”而保留忙等，或写“快照一致”却没有相应同步。
- 范围限于本次新增及受影响代码；保留准确的原注释，不为凑数量重写厂商库、生成代码或无关模块。

例如，与其在忙碌判断旁写“判断忙碌”，更有用的说明是“DMA 尚在读取此发送缓冲，本次返回忙碌，避免覆写在途帧”。只有实际实现符合该行为时才能写这条注释。

## 改码后的缺失与失效检查

每次完成一组代码修改后，先检查“该写但没写”的注释，再检查“已经写但不再正确”的注释；验证中又修改代码则重复此步骤。

1. 对照实际 diff 逐项查看新增/实质修改的文件、函数、类型/字段、参数和关键逻辑块，按上表补齐源码注释；不能只搜索现有注释或统计注释数量。
2. 核对修改处、公共头、直接相关调用点、文件头流程和配置/时序说明，修正参数/返回值、单位、频率、协议布局、上下文、阻塞性、缓冲所有权和状态/错误路径。
3. 删除失效说明，保留正确说明；实现不符合契约时依据任务修正实现或明确差异，不能通过改注释掩盖缺陷，不编造实测结论。
4. 在最终交付前确认没有遗漏本次应注释的代码。交付中简要说明注释补齐/同步结果及涉及位置；没有实际检查时不能宣称已完成。

## 八项架构质量验收

将下列要求用于当前任务涉及的模块或关键链路，不因此扩大为全工程改造。时间预算、数据所有权和接口完成语义优先明确；观测机制和验证深度按资源与风险选择。

| 特征 | 必须回答的设计问题 | 检查依据 |
| --- | --- | --- |
| 实时性可预测 | 周期、截止时间和允许抖动是什么？计算、排队、通信、中断各占多少预算？超期如何处理？ | 关键路径预算和负载下的时延测量；不能只看 CPU 平均占用 |
| 数据与资源归属明确 | 谁更新状态、占用总线、持有缓冲？何时转交和回收？ | 所有者、读写方及状态转换可追踪；不存在无约定的并发写入 |
| 接口完成语义准确 | 返回成功是已接受、传输完成，还是对端确认？忙碌/超时/取消如何通知？ | 公共头契约与所有实现路径一致 |
| 异常可恢复 | 断连、拥堵、陈旧反馈和传输失败后怎样重试、降级或停止？ | 有界异常路径、故障注入和恢复验证 |
| 运行可观测 | 怎样定位超期、丢包、资源耗尽和异常复位？ | 相关计数/时间戳/高水位指标，且诊断开销有界 |
| 核心逻辑可独立测试 | 不接真实设备能否测试算法、协议和状态转换？ | 显式输入输出及主机测试；硬件时序另行验证 |
| 生命周期完整 | 未就绪、初始化失败、停止、取消和重新启动时允许哪些操作？ | 状态与资源清理完整，恢复不执行过期命令 |
| 变化影响范围可控 | 换设备、改协议或调整菜单分别需要改哪些模块？ | 改动集中在所属模块与装配处，避免跨层散改 |

## 按改动选择验证

- 纯算法：边界输入、单位换算、数值域和误差；避免仅复刻实现的测试。
- 协议：有效帧、截断/超长/错误长度、校验错误、拆包粘包、恢复同步、超时和字节序；检查拒绝无效输入后的状态是否仍可用。
- 状态机：正常转换、重复事件、超时、取消、失败恢复和重新进入。
- 并发/负载：队列满、消费者暂停、发送忙、数据一致性、缓冲归还、提交返回前完成、清标志时到达新事件、取消后迟到回调；检查恢复是否退回阻塞路径，非幂等命令是否被错误重试。
- 目标构建：真实工具链、链接符号、段放置和资源占用；主机桩测试不能替代此项。
- 板上验证：实际中断负载、端到端时延、栈余量、总线错误与设备行为。报告测量条件和覆盖范围。

无需每个任务执行全部功能检查；选择与所改边界对应的验证，并清楚报告未验证部分。每次改码后的资源报告是固定交付项，不能以“本次改动较小”为由省略，具体要求见 [资源占用报告](resource-report.md)。

## 构建与再生成检查

每次代码修改后，针对本次目标配置构建并提取资源占用；工具链不可用或构建失败时报告缺口。下列构建配置、链接布局与再生成专项检查按改动选择，不要求每次重建所有板型或运行全部生成工具。

- 保留可追溯的编译器、SDK、生成器版本及板型/产品配置，记录实际构建入口；不依赖个人 IDE 中未保存的宏、包含路径或链接选项。
- 新增源文件核对编译登记、公开/私有包含路径和依赖。检查 App/BSP 的独立性落实到实际包含和链接关系，不能只看目录名称。
- 修改链接布局时检查 map 中 Flash/RAM/栈/堆和 DMA 段，确认预算及放置满足要求；普通编译成功不能证明资源布局正确。
- 仅在使用 CubeMX 的工程中，修改其配置时同步保存 `.ioc`，核对用户代码保留设置与生成差异；条件允许时在工作副本中再生成并构建，检查桥接回调、App/BSP 文件和构建登记未丢失。未实际再生成时明确报告。

ESP-IDF 等组件化项目按其目标配置检查组件依赖、sdkconfig、分区及锁定的依赖；GD32 等固件库工程核对对应系列的启动文件和链接配置。没有生成器的工程不要求 CubeMX 再生成。

CubeMX 的用户区与再生成选项可查 [官方用户手册](https://www.st.com/resource/en/user_manual/um1718-stm32cubemx-for-stm32-configuration-and-initialization-c-code-generation-stmicroelectronics.pdf)，以项目使用的生成器版本为准。

## 交付和审查证据

- 设计说明包含必要假设、职责与依赖、关键接口/数据流/时序及选择理由；按复杂度决定篇幅，不强制生成成套文档。
- 代码交付说明改了什么、为什么改、注释补齐/同步检查结果、进行了哪些验证，以及遗留边界与实机验证缺口；附当前资源报告及同口径前后对比，不仅报告编译成功。
- 分别报告主机测试、目标交叉编译和板上测量，不将模拟结果或成功调用 DMA 当作实时性能证明；实测最大值也不是理论最坏上界。
- 关键假设尚未确认时，标记假设及影响，不能用“运行正常”代替证据。

只报告有调用链、状态流或资源证据的问题。每项说明具体位置、触发条件、影响和最小可行改进；把确定缺陷、设计取舍与待测假设分开。没有适用依据时，不强制 MISRA、功能安全流程、特定 RTOS、动态内存禁令；本 skill 明确要求的 App/BSP 两层结构仍须遵守。
